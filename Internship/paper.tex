\title{Larder: An Intelligent Cross-Platform Recipe App}
\author{Chenye Ni}

\maketitle

\begin{abstract}
This report presents \textbf{Larder}, a cross-platform intelligent recipe application designed to reduce friction across the everyday cooking workflow, from discovering recipes to planning meals, shopping, and in-kitchen execution. Larder addresses common pain points caused by fragmented recipe sources and disconnected planning and grocery decisions by providing an integrated end-to-end journey on iOS and Android. The system combines a React Native (Expo) mobile client with a \mbox{.NET} Web API backend and a PostgreSQL database, supporting persistent user state such as favorites, scheduled meals, shopping items, and dietary constraints. Personalized content discovery is enabled through an embedding-based recommendation pipeline, where offline-generated user and recipe embeddings are stored in \texttt{pgvector} and used for online vector recall with rule-based filtering. To improve practicality in cooking contexts, the step-by-step guidance interface includes timers, keep-awake support, and optional on-device gesture control. Larder also integrates external AI APIs to accelerate common tasks such as recipe drafting from images, ingredient recognition, pantry comparison for missing items, and conversational suggestions, with structured outputs reviewed by users before being committed to app state. The delivered prototype demonstrates a reproducible end-to-end workflow with cross-platform consistency and resilience under imperfect network conditions through local caching and queued synchronization.
\end{abstract}

Recipe recommendation, meal planning, grocery list, cross-platform mobile app, pgvector, gesture interaction, multimodal AI.

\section{Introduction}
In fast-paced daily life, deciding ``what to cook today, what to buy, and how to finish it step by step'' is a frequent decision task with a high cost. Recipe information is highly fragmented. The same dish may be spread across webpages, short videos, and social media. As users save more recipes, the cost of storing and finding them again increases quickly. Video recipes look intuitive, but they often require repeated pausing, scrubbing, and rewatching during cooking. This disrupts the cooking rhythm and increases cognitive load. A more serious issue is that recipe discovery, meal planning, and shopping are often disconnected. When planning meals for the next few days, users need to balance budget, health goals, dietary restrictions, and variety. After the plan is set, they still need to decide what to buy, how much to buy, and how to avoid duplicates with what is already in the fridge. In a real kitchen, wet or greasy hands make touch interaction unreliable. Users still need smooth navigation between steps and quick access to timer information. This creates clear requirements for the execution experience on mobile devices.

This internship project targets these pain points and develops \textit{Larder}, an intelligent cross-platform recipe app for Android and iOS. The goal is to integrate an end-to-end workflow from discovery to management, planning, shopping, and in-kitchen execution. During discovery, the system helps users quickly locate candidate recipes that match personal preferences, time limits, and ingredient constraints. During management, the app supports importing content from different sources, such as links, images, and videos. It then organizes the content into reusable recipe assets. During planning and shopping, users can add dishes to a meal plan and generate a grocery list. Users can also trigger recommendations before cooking based on what is currently in the fridge and then add missing items. During execution, the app provides step-by-step guidance with an embedded timer to reduce interruptions and improve continuity in kitchen contexts. To further reduce the cost of expressing needs, making choices, and taking actions, the system includes a conversational AI assistant. It supports constrained personalized requests, for example lighter meals, higher-protein options, meals finished within 30 minutes, and avoiding repeat purchases. The assistant is connected to in-app functions so that natural language requests can trigger structured actions, such as adding a dish to the meal plan or adding missing ingredients to the grocery list.

While introducing generative AI, the project sets explicit constraints on reliability and scope to avoid untrustworthy or unsafe content in cooking scenarios. The system treats the app database and curated recipe records as the primary source for core functions such as browsing, saving, planning, and grocery operations. AI features are used as an assistance layer. They focus on tasks such as drafting recipes from images, extracting ingredients, and generating suggestions that users can review. The system does not train proprietary models. It avoids maintenance-heavy fine-grained inventory management. It does not provide medical-grade dietary advice. Under model invocation costs and mobile resource limits, the design prioritizes stable behavior and clear user control. AI outputs are presented for review and are only applied to app state after user confirmation. From an engineering perspective, the project adopts a cross-platform architecture to reduce development and maintenance cost. The mobile client is built with React Native. The backend services use C\# and \mbox{.NET}. PostgreSQL is used for data storage to support core capabilities such as recommendations, planning, grocery lists, and user accounts.

This internship is a ten-week project in COMPSCI~778 within the MInfoTech programme at the University of Auckland. It uses a dual-supervisor model with academic and industry guidance. Development is done by a five-person team. The process includes daily stand-up meetings and regular milestone check-ins to support iterative delivery. Within the team, I took primary responsibility for engineering the end-to-end product experience. I independently collected and organized the recipe dataset, which provides the data foundation for retrieval, recommendations, and AI interactions. I implemented the integration of the conversational AI assistant and connected it to in-app capabilities so that it can move beyond simple question answering and support executable operations. On the mobile side, I mainly implemented the front-end for key pages, including Discover, Grocery, Profile, Meal Plan, and the Step-by-step Guide. I also handled the front-end packaging workflow and participated in backend deployment and integration to ensure the system runs end-to-end and can be demonstrated. Gesture recognition, the Discover recommendation algorithm, login, and the core backend and database implementation were completed by other team members. My work focused on data and AI integration, mobile experience construction, and the engineering effort required to close the end-to-end delivery loop.

\section{Literature Review}

Collecting recipes at scale is not difficult. The hard part is data quality and consistency. Recipe1M+ shows the value of recipe text and food images for learning and retrieval tasks. It also reports common issues in web-scale recipes. Formats are inconsistent. Records are duplicated. Text contains semantic noise. If raw data is used directly, retrieval and recommendation can be disrupted by ingredient aliases, messy units, and missing steps~\cite{marin2021recipe1mplus}. This implies that data engineering is not an optional preprocessing step in recipe systems. It is core infrastructure that sets the upper bound of later modules. Recipes need a consistent representation. It should include ingredients, units, ordered steps, total time, and filterable attributes. These structured fields enable stable execution in later modules. They support filtering and ranking in \textit{Discover}. They support scheduling in \textit{Meal Plan}. They support de-duplication and aggregation in \textit{Grocery}. They support step rendering and timer logic in step-by-step guidance.

Once the data layer is consistent, the discovery stage becomes a recommendation and retrieval problem with both personalization and constraints. Surveys on food recommendation note that recipe recommendation is more context dependent than general content recommendation~\cite{trattner2017food_recommender_systems}. Choices depend on dietary preference, cultural and health constraints, available ingredients, and time budget. Data sparsity and cold start make coverage difficult. Classic recommender system surveys also stress that recommendation is not a single algorithm problem~\cite{adomavicius2005next_generation_rs}. It is a system problem that combines user modeling, item modeling, and a feedback loop. These surveys propose extensions such as context awareness, multi-criteria signals, and knowledge-based components. In recipe scenarios, the system should predict what users may like. It should also enforce conditions that must be satisfied. These conditions must influence candidate generation and ranking.

A constraint satisfaction view is clear in the work by Chen et al.~\cite{chen2021personalized_food_kbqa}. They model personalized food recommendation as constrained question answering over a large food knowledge graph. They argue that real queries often include hard constraints and soft preferences. Similarity matching alone does not guarantee executable results. This view has direct product implications. \textit{Discover} and search should map natural language preferences, time requirements, and ingredient restrictions into structured filters and ranking signals. The system then executes these constraints on normalized fields. At scale, industry systems often use a two-stage design. It separates candidate retrieval from ranking to balance throughput and quality~\cite{covington2016youtube_dnn_recs}. This design aligns with vector-based semantic matching. DSSM maps queries and documents into a shared semantic space. It reduces the limits of pure keyword matching~\cite{huang2013dssm}. In implicit feedback settings, ranking objectives often match behavior signals better than pointwise labels. BPR optimizes a pairwise ranking objective under implicit feedback. It fits signals such as clicks, views, and favorites~\cite{rendle2009bpr}. Neural collaborative filtering shows that non-linear user item interaction models can improve expressiveness~\cite{he2017neural_collaborative_filtering}. When short-term intent matters, sequence models help capture session-level shifts. Session-based recommendation with recurrent neural networks is one example~\cite{hidasi2015session_rnn}. Together, these studies form the technical background for personalized discovery. A system can rely on implicit behavior as the main signal. It can combine vector recall with ranking to scale while preserving individual preference.

In the workflow of \textit{Larder}, discovery is not the end. \textit{Meal Plan} and \textit{Grocery} expand the task. The problem moves from choosing one dish to planning an executable set over time. The system then produces a checkable shopping list. This shift from content consumption to decision execution requires recipes to be treated as composable planning units. Ingredients need to be aggregatable. Units need to be convertible. Synonyms need to be merged. Otherwise cross-recipe summaries become noisy and hard to use. The constraint view still applies. Plans often include budget, time, preferences, and duplicate avoidance. The system should map these conditions into structured rules. It should also present results in an explainable way~\cite{chen2021personalized_food_kbqa}. Hybrid recommender research supports combining information sources and strategies for robustness under sparsity and complex constraints~\cite{burke2002hybrid_recommenders}. In recipe applications, this hybrid idea can appear in recall. It can also appear in ranking. Hard constraints can be enforced by rules. Soft preferences can be handled by learned ranking. This helps connect discovery, planning, and shopping under a consistent data model and constraint logic.

Beyond decision support, the execution stage introduces clear context and interaction challenges. HCI studies show that cooking splits attention and keeps hands busy. Users shift between the bench, the stove, and ingredients. Touch interaction is affected by wet or greasy hands and hygiene concerns~\cite{nansen2014kitchen_kinesics}. In this setting, gestures need to be usable and avoid false triggers. They should also fit natural behavior in family cooking. Work on kitchen displays and contactless interaction suggests that gesture control can reduce hygiene cost and interruptions~\cite{besevli2022gestural_kitchen}. Its effectiveness depends on clear feedback and learnable mappings. From an engineering view, on-device real-time hand tracking has been demonstrated with MediaPipe Hands~\cite{vakunov2020mediapipe_hands}. It supports low-latency gesture recognition on mobile devices. These studies support the design direction for step-by-step guidance. The execution interface should keep steps clear and pacing controllable. It should reduce reliance on touch for navigation, timing, and review. This matches real kitchen constraints.

\textit{Larder} also introduces a conversational assistant. It uses natural language as the entry point for preferences and operations. Recent work on language models shows that models can generate text and coordinate with tools in a reasoning and acting loop~\cite{yao2023react}. This sets a clear goal for dialogue in recipe applications. Dialogue should not stop at advice and explanations. It should drive structured state changes inside the app. It can add a recipe to a plan. It can add missing items to a shopping list. It can adjust a plan under user constraints. A conversational interface lowers the barrier to express constraints. It also links discovery, planning, and shopping into one continuous flow. Users can move from intent to action in a single channel.

\section{Success Criteria}

The core goal of this project is to deliver an intelligent recipe app prototype that runs on both Android and iOS. The prototype should support an end-to-end workflow that covers discovery, management, planning, shopping, and cooking execution. Success is not measured by the number of features. It is measured by whether key user journeys form a stable closed loop. When a user completes a real task in the app, each step should have clear inputs and outputs. Each step should also produce persistent state changes. These states should be reusable and verifiable in later steps. Under the constraints of a ten-week project, the success criteria include functional goals and non-functional quality goals. The final baseline requirement is that the system is demonstrable, reproducible, and deployable.

On the functional side, the system should provide a complete set of core modules. Data and interactions should connect across modules without breaks. The \textit{Discover} module should provide an actionable browsing experience. It should support personalized recommendations and basic filtering. Users should be able to find candidate recipes with reasonable effort. Users should also be able to save recipes for later use. The recipe management capability should support importing content from external sources. Imported content should be presented in a consistent format. Key fields should be readable and clearly structured. These fields include the title, ingredients, steps, and total time. This ensures reliable inputs for planning and shopping list generation. The \textit{Meal Plan} module should allow users to add recipes to a specific date or time window. Users should be able to view, adjust, and delete planned items. These changes should be reflected immediately in later shopping list logic. The \textit{Grocery} module should generate an executable shopping list from the plan. List items should come from structured aggregation of recipe ingredients. The list should support real shopping actions. Users should be able to check items off and delete items. The list should also support necessary merging and de-duplication. This avoids a formal output that cannot be used in practice. The \textit{Profile} module should save user preferences and basic settings. These settings should have a visible impact on discovery, filtering, and dialogue interactions. This creates a minimal personalization loop. Login and authorization should bind user data and personal state to an account. This includes favorites, plans, lists, and preferences. The system should persist this state across sessions. The step-by-step guidance interface should let users follow a recipe in order, step by step. The presentation should be clear and pacing should be controllable. The interface should provide timers and keep-awake support to reduce interruptions. The system should also support non-touch step control. Users should be able to move forward and move backward. Users should also be able to review a step again. This should work even with wet or greasy hands. False triggers should be controllable. Feedback should be clear. The mappings should be learnable. These conditions should improve usability in the execution stage.

For the \textit{Discover} recommendation algorithm, success is not only that the model can be trained or run offline. It also means the model can be called reliably inside the app. It should produce explainable product value. The system should generate personalized candidates based on user profiles and in-app behavior signals. These signals include search, clicks, favorites, and ratings. The results should be presented in a way that fits mobile interaction patterns. The recommendation pipeline should support repeatable training and update procedures. The team should be able to reproduce model building and deployment in a shared environment. At the outcome level, small-scale testing or offline checks should show signs of improvement over simple baselines. Baselines can be popular, newest, or category-based ranking. Improvements can appear in relevance, coverage, or personalization differences. The system should not frequently degrade into an unusable state due to sparsity or cold start.

For gesture recognition and non-touch control, the success criteria require basic usability in kitchen-like conditions. Under typical lighting and a reasonable holding distance, gesture triggers should have acceptable latency and stability. They should support core operations such as moving to the next step and moving to the previous step. The false trigger rate should stay low enough that it does not disrupt cooking rhythm. The system should provide clear feedback so users understand the current recognition state. When gestures are not available, users should still complete the same operations with touch. This avoids a single point of failure where a gesture failure breaks the flow.

The success criteria for the conversational AI assistant focus on practical gains for the workflow. They do not focus on richer generated text. The system should understand common intent expressions that relate directly to recipes, plans, and lists. The system should convert them into verifiable outcomes. It should either return candidates and explanations based on existing content. It should also be able to trigger clear in-app actions and change observable state. Examples include adding a recipe to the \textit{Meal Plan}. Examples also include adding missing ingredients to \textit{Grocery}. Another example is updating user preference settings. The project scope does not include medical-grade dietary advice or high-risk health judgments. AI outputs should stay within a controlled range. The system should not provide diet prescriptions with medical claims. The system should not generate critical facts that could mislead execution when there is no supporting app data. The interface should clearly communicate capability boundaries to users.

On data quality, success requires the underlying recipe corpus to support stable operation of the features above. Data should be consistent, parsable, and extensible. Recipe records should be stored in a unified structure. They should render reliably on the client. Ingredient fields should be granular enough for aggregation. Measurement units and naming should be as consistent as possible within the corpus. This reduces cases where grocery aggregation fails due to naming mismatches or unit confusion. Success does not require a perfectly noise-free dataset. It does require that missing key fields do not systematically break user journeys. Grocery list generation should not fail frequently due to missing ingredients. The execution interface should not fail to load or progress due to missing steps.

On non-functional quality, the success criteria emphasize cross-platform consistency, stability, acceptable performance, and deliverability. Cross-platform consistency means key pages and core flows work on both Android and iOS. Platform-specific adaptations are acceptable. A flow should not break because a core capability is missing on one platform. Stability means the app should not show reproducible crashes or blocks on typical user paths. This is especially important for browsing in \textit{Discover}, saving recipes, adding plans, generating lists, entering step-by-step guidance, and triggering key actions through AI or gestures. The project does not target extreme performance. Core interactions should stay within an acceptable range for users. Page transitions and list scrolling should not stutter noticeably. List generation and plan updates should not block the interface for long periods. Dialogue requests should have clear loading feedback and timeout handling. This prevents users from assuming the system is unresponsive. Deliverability means the team should provide a reproducible build and deployment process. The team should be able to package the client and deploy the backend in an assessment environment. The team should also produce a demonstrable system build.

To make these criteria verifiable, acceptance focuses on scenario-based task completion. Visible system state is used as evidence. A typical acceptance scenario includes the following path. The user obtains personalized candidates from \textit{Discover} and saves a recipe. The user adds it to \textit{Meal Plan} on a chosen date. The user generates and checks a \textit{Grocery} list. The user then enters step-by-step guidance and follows steps to cook. The user uses the timer, keep-awake, and gesture capabilities during the process. Another scenario uses the conversational assistant. The user inputs constraints or an operation intent. The observer checks whether the system returns results consistent with app data. The observer also checks whether the system triggers verifiable state changes. If these scenarios can be repeated on both platforms, then the delivery meets the success criteria. Key states should persist and remain accessible for later reuse.

\section{Methodology}

This project uses an agile approach to organize team collaboration and delivery cadence. The goal is to complete a cross-platform end-to-end prototype within ten weeks. Requirements also evolve during research and implementation. The team therefore follows three principles. The first principle is rapid iteration. The second principle is continuous feedback. The third principle is to deliver a usable closed loop early. The team sets short-cycle goals and keeps work visible through daily synchronization and a task board. At the end of each iteration, the team demos progress and reviews outcomes. The team then adjusts direction and priority for the next iteration. This helps maintain controllable progress and quality under uncertainty.

Work is organized in sprints. Each sprint defines a clear delivery goal and scope. The goal is then decomposed into tasks that are implementable and verifiable. At the start of a sprint, the team prioritizes tasks based on the overall milestone plan and current risks. The team selects core features that must be completed. The team also identifies enhancement items that can be delayed if needed. At the end of a sprint, the team reviews what was completed and why some work was not completed. The team also reviews technical risks and collaboration issues that emerged during implementation. These results guide the next sprint plan and task assignment. Periodic presentations act as sprint-level checkpoints. Before each checkpoint, the team prepares a demonstrable build or a focused prototype of a key feature. After each checkpoint, feedback is converted into actionable tasks for the next sprint. This reduces the risk of late integration and late fixes.

For daily collaboration, the team uses a stand-up meeting as a low-cost communication mechanism. Each morning, members quickly synchronize on what they finished yesterday, what they plan to do today, and what blockers they face. This process exposes task dependencies early and supports timely coordination. It also keeps the team aligned without adding heavy meeting overhead. The project includes multiple technical tracks. These tracks include mobile screens, recommendation logic, gesture interaction, login and authorization, backend services, and the database. In practice, the stand-up also supports early interface alignment across modules. When an API or a data structure changes, the team assesses impact on the same day. The team then schedules integration work and fixes. This helps avoid a burst of integration failures near the end of a sprint.

Task management is done on GitHub. As shown in Figure~\ref{fig:github_board}, the team maintains a task board in GitHub Projects. Requirements and implementation work are decomposed into tasks with manageable granularity. Each task card records priority, estimated effort, assignee, target deliverables, and acceptance conditions. This makes work traceable. It clarifies what to do, who does it, and what counts as done. Tasks move across board states such as to do, in progress, and done. Team members update status and key progress during implementation. The board remains transparent to all members. Priorities are adjusted during a sprint when progress or external feedback changes. Low-priority items can be moved out of the current sprint. This protects delivery of risk-critical work and maximizes value under limited time.

For delivery and integration, the team prioritizes early integration and continuous runnability. Each sprint plan protects a runnable main path. Enhancement features can remain incomplete without breaking the core flow. Mobile and backend integration is driven by verifiable interfaces. Important data structures and API agreements are clarified at the task stage. Prototype interfaces are then replaced with stable interfaces through small incremental steps during implementation.

\section{Architecture}

\subsection{Overall layering and component boundaries}

The overall architecture is shown in Figure~\ref{fig:arch_overview}. The mobile client uses Expo React Native for cross-platform UI and orchestration. The screen layer covers core scenarios. These scenarios include \textit{Discover}, \textit{Recipe}, \textit{Meal Plan}, \textit{Grocery}, \textit{Profile}, and step-by-step guidance. To reduce coupling between screens and backend details, HTTP calls are wrapped in a dedicated API client layer. The client also maintains a local cache and a sync queue based on SQLite and AsyncStorage. This keeps the app usable under unstable networks. It also supports change synchronization after connectivity returns. The backend uses ASP.NET Core Web API. It organizes endpoints around REST resources. Controllers handle routing and parameter validation. Business rules are aggregated in a service layer. The service layer accesses PostgreSQL through a repository layer. Authentication follows a Google token exchange pattern. After Google sign-in, the client sends an idToken to the backend for validation. The backend then issues an application JWT. This JWT is used as the identity context for later requests. PostgreSQL is the primary storage layer. It stores core tables for users, recipes, plans, lists, and behavior logs. It also stores embedding vectors for recommendations. The system uses pgvector for nearest neighbor search. Model training and vector updates run as an offline pipeline. The pipeline reads behavior and profile data. It produces user and recipe embeddings. It then writes embeddings back to the database for online recall.

Figure~\ref{fig:arch_overview} also reflects a key trade-off. Online recommendations do not depend on a separate inference microservice. The system uses database vector search for candidate recall. The backend then applies rule-based filtering and de-duplication. This reduces deployment and operations cost. It fits the delivery constraints of a ten-week project and a small team. It also leaves room for future upgrades. Offline embedding updates and model version management can evolve over time. Online recall can remain stable.

\subsection{Backend architecture}

The backend follows a layered structure that separates responsibilities. The controller layer exposes REST endpoints. It covers resources such as recipes, favorites, scheduled recipes for meal planning, shopping items for grocery lists, user preferences, and sync. Data contracts are fixed through DTOs. This keeps field conventions stable during iteration. The service layer aggregates business rules. Examples include assembling recommendation responses, selecting translations based on locale, computing favorite state, and handling plan and list writes. The repository layer interacts with PostgreSQL. It supports standard CRUD operations. It also wraps pgvector-based candidate recall queries. This allows the recommendation module to reuse data access without breaking service boundaries. Cross-cutting concerns are centralized. These concerns include unified exception handling, request validation, and logging. Middleware and validators manage them. This avoids scattering error handling and validation across controllers. It improves maintainability.

The system uses Google sign-in as the identity source. The backend validates the idToken. It also creates or binds the user record. It then issues an application JWT. This decouples third-party identity from application authorization. After token exchange, user-scoped endpoints only need to verify the application JWT. They can then obtain a userId context and apply access checks. This model also simplifies the mobile client. The API client can attach \texttt{Authorization: Bearer <JWT>} to requests. The client does not need to manage complex backend auth state. This project is a fast-iterating prototype. Test users can be configured during development to reduce integration blockers. A production release should enforce authorization for all user-scoped writes and privacy-sensitive reads. The backend should also apply strict resource access control.

\subsection{Data layer and core data model}

PostgreSQL is used as the single source of truth. It stores business state and recommendation vectors. Core tables are organized around users and recipes. The user side includes profile fields, dietary preferences, and allergy constraints. The recipe side includes ingredients and ordered steps for execution. The workflow side uses \texttt{ScheduledRecipes} for meal plans and \texttt{ShoppingItems} for grocery lists. The behavior side uses tables such as \texttt{RecipeViews} and \texttt{CookingLogs}. It can also be extended with ratings and recommendation delivery logs. These signals support recommendations and product analysis. To support multilingual presentation, the database maintains translation tables for recipes, steps, and ingredients. The backend selects the most suitable text fields based on the client locale. This avoids scattering translation logic across the mobile client. To reduce the impact of naming variants on aggregation and filtering, the database also includes a standard ingredient dictionary and mapping relations. It supports fuzzy matching and improves consistency.

Figure~\ref{fig:data_model} summarizes relationships among the core data objects. The diagram omits tags, translations, and conversation records to keep it readable. These extension tables do not change the main workflow dependencies. They support multilingual features, content operations, and AI interaction traces.

The mapping between this data model and the workflow is direct. Candidate generation and filtering in \textit{Discover} depend on user constraints and recipe attributes. Meal planning depends on the relation between \texttt{ScheduledRecipes} and \texttt{Recipes}. Grocery list maintenance depends on \texttt{ShoppingItems} and their references to \texttt{Ingredients}. Step-by-step guidance depends on the order and content of \texttt{RecipeSteps}. Explicit relational modeling with foreign key constraints helps keep state consistent during iteration.

\subsection{Recommendation pipeline}

The recommendation pipeline combines offline training and updates with online vector recall and rule filtering. In the offline stage, a Two-Tower style model produces user embeddings and recipe embeddings. Vectors and model versions are written into embedding tables in PostgreSQL. In the online stage, the client requests personalized recommendations for \textit{Discover}. The backend reads the user vector from the database. It then performs nearest neighbor search on pgvector to obtain candidate recipeIds. The backend applies constraints and rules. These rules include dietary preferences, allergies, time limits, and de-duplication based on previously delivered recommendations. The backend then assembles recipe cards in one response. The mobile client can render them directly. This design moves expensive deep model inference to the offline stage. Online performance pressure is concentrated on database vector search and lightweight backend assembly. It improves deliverability and debuggability for a small team.

To improve product consistency, the backend also provides supporting lists. Examples include quick, popular, recently viewed, and recently cooked. These lists can populate different \textit{Discover} sections. They can also act as fallback paths when personalized vectors are missing or cold start occurs. This reduces the chance of an empty feed for first-time users. It also leaves room for later strategy fusion and A/B adjustments.

Figure~\ref{fig:rec_flow} shows the key call chain for personalized recommendations in \textit{Discover}. The backend does not return a raw list of recipeIds. It returns a DTO list assembled in ranking order. This avoids extra detail fetches from the client. It reduces mobile network overhead. It also improves first-screen latency.

\subsection{In-kitchen execution}

The core execution interface is step-by-step guidance. It splits a recipe into ordered step cards. It also integrates timers and keep-awake support to reduce interruptions during cooking. Touch interaction can be inconvenient in a kitchen. Users may have wet or greasy hands. The system therefore integrates gesture control on the client. It uses a WebView that runs MediaPipe Hands. React Native performs gesture classification and action mapping. Camera frame processing and landmark detection run inside the WebView. The landmark sequence is sent back to React Native through \texttt{postMessage}. A classifier detects gestures. The page then maps gestures to actions. Actions include next step, previous step, start or resume the timer, and reset the timer. To reduce disruption from false triggers, the gesture module uses cooldown logic. It also outputs no action when recognition is unstable. It prefers no trigger over a wrong trigger. When initialization fails or runtime errors occur, the system disables gestures and falls back to touch controls. The main flow continues. This makes gestures an enhancement rather than a dependency. It matches robustness needs in real kitchens.

\subsection{AI capability integration}

AI capabilities are used to lower the barrier for content import and decision expression. Features include conversational recipe suggestions and grocery suggestions, photo-based ingredient recognition, OCR from recipe images into drafts, and speech transcription. The project does not train custom models. AI is provided through external model APIs. The client organizes requests, parses responses, and presents results. To avoid uncertainty from direct writes, state changes follow a conservative strategy. Model outputs are returned as structured JSON. The client parses the JSON and shows results as cards. Users then confirm before any write. Confirmed actions call existing backend APIs and update core tables. These tables include \texttt{ScheduledRecipes}, \texttt{ShoppingItems}, and \texttt{Recipes}. In this design, AI acts as a helper rather than the sole source of truth. Even when outputs have format errors or unreliable content, the app can remain controllable. It can fall back to plain text. It can also request user edits and confirmation.

\section{Implementation}

\subsection{User flows and navigation}

Figure~\ref{fig:navigation} summarizes the mobile navigation design. We use a combined structure. It includes a launch router in \texttt{RootStack}. It also includes five fixed entry tabs. Key secondary pages are handled by a stack and modal routes. After launch, the app enters \texttt{AuthLanding}. This screen restores session state and decides the entry path. If a valid session token exists, the app resets navigation and enters \texttt{MainTabs}. If no token exists, the app enters \texttt{GoogleLogin}. Users can complete Google sign-in and obtain an app JWT. Users can also skip sign-in and continue as a guest. If the user is new, the app routes to \texttt{UserRegistration}. This step collects minimal profile data and initializes preferences and constraints. This design decouples identity from the main workflow. Core pages do not need complex auth branching. They rely on a unified session service that provides \texttt{userId} and \texttt{token}.

After entering the main flow, the bottom tab bar provides five stable entries. They map to \textit{Discover}, \textit{Planner}, \textit{AI}, \textit{Groceries}, and \textit{Profile}. The AI tab uses a special interaction. It opens a full-screen \texttt{AIModal} instead of switching to a persistent page. This modal hosts high-frequency AI tasks. It includes chat, image recognition, and OCR drafts. This design makes AI available at any time. It also reduces context loss from frequent page switching. In parallel with tabs, \texttt{RootStack} maintains secondary pages. Examples include \texttt{RecipeDetail}, \texttt{SectionDetail}, \texttt{StepPlayback}, \texttt{Favorites}, \texttt{BrowsingHistory}, \texttt{MonthlyStats}, and \texttt{DietaryPreferences}. These pages support deeper browsing, editing, and execution tasks. Admin users with \texttt{isAdmin} have additional routes. They include \texttt{AdminRecipeRecommendations}, \texttt{AdminRecipeDetail}, and \texttt{AdminRecipeEdit}. These routes support setting and reviewing Editor's Pick content.

\subsection{Global state and infrastructure encapsulation}

For cross-screen state, we use a lightweight global state approach based on React Context. We also separate responsibility boundaries from persistence locations. \texttt{LanguageProvider} manages language and localization. It restores the saved language at startup. It also stays in sync with i18n language change events. \texttt{ToastProvider} manages toast messages. It exposes a single \texttt{showToast()} API to business pages. This avoids duplicated success and failure UI. \texttt{QueueProvider} manages the meal plan queue. It supports optimistic updates and weak network tolerance. \texttt{GroceryProvider} manages the grocery list. It stores a local copy and runs offline queue synchronization with the server. Provider ordering ensures that base capabilities such as language and safe area handling are applied first. Business state is injected before the navigation container. This lets every screen access consistent state through hooks.

Session state is implemented with a centralized session service and automatic API client injection. The session service persists \texttt{userId} and \texttt{token}. It also provides unified async access. The API client centralizes base URL selection, token injection, locale propagation, response envelope unpacking, and error classification. Screen code can then call \texttt{api.get}, \texttt{api.post}, \texttt{api.put}, and \texttt{api.delete}. Backend responses use an envelope type. The client unwraps \texttt{data} automatically. The client throws a structured \texttt{ApiError} on failures. Failures include network errors, non-2xx HTTP responses, and cases where \texttt{success} is false. The error object contains the error kind, status code, backend error list, and request metadata. This reduces page-level complexity. It also keeps error handling consistent across screens.

\subsection{Discover section feeds and caching}

The \textit{Discover} page aims to meet several product requirements. The feed should be rich. It should support getting a new batch. Sections should avoid duplicates. Results should stay consistent across languages. We implement the feed as multiple sections. They include Editor's Pick, For You, Quick \& Easy, Popular This Week, Recently Viewed, and Recently Cooked. Each section maps to a dedicated backend endpoint. The client loads sections in one screen and assembles a sectioned list. To reduce duplication, the client passes cross-section exclusion sets. Later sections send \texttt{excludeIds} that include recipeIds already shown in earlier sections. Pull-to-refresh applies a similar approach. For You excludes part of the current list to produce a more reliable new batch. Quick and Popular then update their exclusion sets based on the refreshed For You results. This keeps duplication low after refresh.

Client-side exclusion alone is not sufficient in all cases. Repeats can still occur when users refresh many times. The candidate pool can also be small. The backend therefore maintains a sent history for recommendations. Online recommendation endpoints prioritize candidates that have not been sent. When candidates are insufficient, the backend rotates older sent items. It selects items that were sent least recently. It also updates the sent timestamp for the current response. This provides a baseline rotation even without \texttt{excludeIds}. In this design, \texttt{excludeIds} targets short-term de-duplication and immediate novelty. The sent history supports medium-term rotation and repeat avoidance. The combination improves usability without requiring an online re-ranking service.

To control network cost and stabilize the first screen, \textit{Discover} uses data-version driven cache invalidation. The backend provides a \texttt{dataVersion} endpoint. It returns a compact string that reflects global changes in recipe data. The client binds cache keys to a \texttt{userKey}, a \texttt{locale}, and \texttt{dataVersion}. When language changes or the data version changes, the client clears \textit{Discover} caches and reloads. Each section also uses a daily cache key. This reduces repeated requests within the same day. It refreshes automatically across days. The key trade-off is simple. Cache invalidation is decided by a server-side version. The client does not need to guess whether data has changed.

\subsection{Recipe detail interactions and state writes}

\texttt{RecipeDetail} connects discovery, planning, shopping, and execution. The implementation focuses on two goals. Users should complete frequent actions on one screen. Each action should produce traceable state changes. The screen supports favoriting, serving adjustment, adding to \textit{Meal Plan} now or later, and adding ingredients to \textit{Grocery}. Users can add a single item or all ingredients. The screen also provides an AI entry point through \texttt{AIModal}. This supports tasks such as suggestion generation and missing item checks against pantry input. Favoriting writes through the backend favorites API and updates local state. Planning writes optimistically through \texttt{QueueProvider}. It then syncs to the server in the background. Grocery writes optimistically through \texttt{GroceryProvider}. The operation is recorded in an outbox queue and synced later. Entering cooking mode routes to \texttt{StepPlayback}. The step sequence is the main interaction axis. The experience is designed to reduce interruptions.

Serving adjustment uses proportional scaling at the presentation layer. The screen scales ingredient quantities without modifying stored recipe data. It keeps original ingredient units. This supports quick estimation for shopping. Units vary widely across recipes. Examples include one onion, 200 g chicken, and one tablespoon oil. Grocery writes therefore store structured fields. They include ingredientName, quantity, and unit. Later merging and unit normalization are handled in the grocery layer. This avoids coupling complex unit logic into the detail screen.

\subsection{Meal Plan}

\textit{Meal Plan} uses \texttt{ScheduledRecipes} as the server-side persistent object. On the client, \texttt{QueueProvider} maintains a local queue as immediate feedback. When a user adds a plan item from the detail screen, the client writes the schedule into the local queue first. The \textit{Planner} screen updates immediately. A background sync task then calls \texttt{POST /api/scheduled-recipes} to persist the item. The plan view primarily reads from the local queue. This keeps the experience responsive under weak networks. Deletion uses a pending delete mechanism. If a delete request fails, the intent is stored locally. It is retried in later sync cycles until the server confirms deletion. Sync runs on a fixed interval. It also runs when key pages gain focus. This reduces inconsistency caused by missed background windows.

For consistency, server responses are treated as the final source of truth. When needed, the client calls \texttt{GET /api/scheduled-recipes}. It then aligns the local queue with server state. This repairs occasional sync failures and cross-device changes. Schedule times are stored and transmitted in UTC. The client converts to local time for display. This avoids time shifts across devices and time zones. The current product path focuses on adding and deleting schedule items. The backend supports schedule time updates. The mobile UI does not expose an edit entry yet.

\subsection{AI integration}

Model outputs are represented as structured JSON. Any write that changes system state requires user confirmation. In the current version, AI integration is implemented mainly on the client. It covers chat recipe suggestions, chat grocery suggestions, pantry missing item comparison, photo-based ingredient recognition, OCR drafts from recipe images, and speech transcription. Different providers expose different interfaces and return formats. The client therefore uses a unified parsing strategy. It first extracts a \texttt{json} code fence if present. If not, it extracts the most likely \texttt{\{...\}} or \texttt{[...]} region. It then runs \texttt{JSON.parse} and applies minimal field checks. If parsing succeeds, the UI renders a card or a draft form. If parsing fails, the UI falls back to plain text and offers retry. For grocery and missing-item outputs, users can remove items and confirm. After confirmation, the client calls \texttt{POST /api/shopping-items} for each item. The outbox queue preserves eventual consistency under weak networks. For OCR drafts, the UI fills an editable form. After saving, the client calls \texttt{POST /api/recipes} to store a formal recipe. Speech transcription mainly enhances input. It does not write to the database. It supports dictation mode for text input. It also supports command mode for execution control.

\section{Results}

The delivered build provides a repeatable main path on both iOS and Android. Key states remain consistent across restarts and page navigation. This shows a move from a screen prototype to a state-driven runnable app. When the network is unstable or some external dependencies fail, core pages remain usable. After conditions recover, the app returns to a consistent state.

Results on \textit{Discover} are reflected in controllable distribution and a usable novelty experience. Different user constraints lead to observable differences in candidate sets. Cross-section duplication is reduced by exclusion sets and server-side rotation. Multiple refreshes produce some content rotation. The list does not repeatedly return the same items. Novelty decreases when the candidate pool becomes small due to strong hard constraints. This is a boundary caused by data scale and constraint strength. It is not an implementation defect.

Results on \textit{Planner} and \textit{Grocery} are mainly about practical usability. Schedule add and delete actions apply immediately on the UI and persist reliably. The grocery list supports add, edit, check-off, and delete actions. It also performs merging and unit normalization at the presentation layer. Under weak networks, interaction continuity is a clear benefit. List editing does not require each request to succeed immediately. Local updates happen first and background sync follows. The current version does not generate \textit{Grocery} from \textit{Meal Plan} by default. This keeps the list flexible and user controlled. It also limits automation.

The cooking execution interface remains stable in continuity. Step following, timers, and keep-awake support reduce interruptions during cooking. Gesture control supports next and previous step navigation and timer control under typical indoor lighting and a reasonable holding distance. If permissions are missing, initialization fails, or recognition becomes unstable, the system falls back to touch controls. The execution flow continues. AI benefits focus on turning unstructured inputs into editable structures. Vision recognition and OCR produce drafts that enter the recipe management flow. Chat outputs are shown in a structured form. They become list items or recipe objects only after user confirmation. When parsing fails or input quality is poor, the system falls back to plain text and manual editing. It does not write unreliable content into persistent state.

Validation in this project focuses on system-level runnability and consistency. A strict quantitative evaluation loop is not yet in place. Examples include offline metric comparisons for recommendations, statistics on gesture false triggers, and sync success and recovery time under different network conditions. These gaps do not change the current conclusion. The prototype is runnable, deliverable, and demonstrable. The gaps do affect academic strength. Future work should add more systematic experiments and data logging.

\section{Reflection}

Looking back on these ten weeks, my biggest gain was not simply building features. I learned how to work under uncertainty, tight time limits, many dependencies, and intensive collaboration. I learned how to break a large system goal into engineering problems that are verifiable and deliverable. I then solved them one by one in a cautious way. Early in the project, I worried that I would slow down progress while chasing a perfect architecture. This product spans the client and the backend. It also spans the data model, recommendations, on-device interaction, and AI integration. If any one chain becomes unstable, the final outcome can become a set of partial pages. It would not be a runnable closed loop. To avoid this risk, I forced myself to redefine delivery as one repeatable user journey. I then ranked tasks around that journey. I first ensured that each page had usable inputs and outputs. I also ensured that key states could be written and read again. After that, I improved the experience and added enhancements. This choice made my work feel like pushing the system from unusable to usable. It did not feel like polishing local details. It also showed me that engineering maturity often comes from scope and risk control. It does not come from stacking more technical tricks.

My biggest frontend challenge came from context switching and integration risk. I worked on multiple core modules at the same time. In mobile development, a screen often handles UI state and network calls. It also handles errors, caching, and navigation. When an interface or a field changes, it can trigger cascading edits across many screens. At first, I tried to track these changes in my head. I quickly found that I kept repeating small mistakes. Some requests missed \texttt{locale}. Some screens did not handle the API envelope in a consistent way. Some weak-network cases missed a fallback path. I then changed my approach. I forced reusable capabilities into shared layers. Screens kept only minimal orchestration logic. In practice, I centralized API calls, token injection, error classification, and toast messages. I also centralized shared queue and list state through Providers. This did not reduce code immediately. It reduced fragility during iteration. When an interface changed, I no longer needed to patch many screens one by one. I could fix it in a few entry points and the whole app benefited. This made me understand maintainability in a more concrete way. It is not an aesthetic concern after coding. It is a practical need that reduces rework during delivery.

In teamwork, my clearest change came from letting go of the idea that I should do everything alone. At the start, I preferred to finish tasks by myself. It seemed faster. It also avoided communication cost. In a real team cadence, this fails in two ways. One person cannot make the best product decisions and the best technical trade-offs at the same time. One person also cannot keep the most stable delivery pace when the system becomes complex. There is another issue. Requirements keep evolving during discovery. Working in isolation often delays problems until integration. As stand-ups, code reviews, and conflict discussions progressed, I became more willing to surface blockers early. I turned them into visible team tasks. I also used discussion to converge faster. When we disagreed, I learned not to insist that I was right. I learned to turn debate into a testable hypothesis. We used small prototypes or comparisons when possible. We did not rely on subjective arguments.

I also developed a more concrete understanding of engineering ethics. It is not a slogan. During development, I stayed sensitive to two types of risk. One is user data and identity security. The other is the responsibility boundary of AI content. Even in a prototype, I treated authentication, token handling, and sensitive data care as engineering requirements. I did not treat them as optional work after the main flow runs. For AI outputs, I insisted on user feedback and correction space. I avoided presenting model outputs as authoritative conclusions. These practices reminded me that professionalism is not only code quality. It also includes responsibility to users and honest communication of system boundaries.

If I summarize the change in one sentence, it is this. I no longer treat finishing everything alone as the only goal. I prefer to place myself in a real software engineering context. I solve problems in a deliverable, collaborative, and maintainable way. The challenges did not disappear. I learned more controllable ways to face them. I also became clearer about what I still need to strengthen next.

\section{Conclusion and Future Work}

The core value of this internship is not a single technical point. It is the delivery of an application that supports multi-stage user tasks. The project starts from requirements and constraints. It ends with a deliverable system outcome. For me, this delivery shows that I can narrow scope within a limited cycle. It also shows that I can integrate modules and land engineering work. I defined boundaries and failure paths at key points. This kept the system controllable under high uncertainty.

Future work should first add evaluation and observability. Iteration should not rely on subjective feel or demo impressions. It should rely on traceable metrics. Recommendation and retrieval should be evaluated on coverage, diversity, and constraint satisfaction. Plans and lists should be evaluated on eventual consistency and recovery behavior under different networks. Execution stage interaction should be evaluated on false triggers and interruption rates. The AI assistance pipeline should be evaluated on success rates from input to executable structure. It should also measure user edit cost. This requires more systematic event logging and instrumentation. It also requires replay tools and small experiments that can be reproduced. These steps can build an evidence chain that is stronger for academic writing.

The prototype should then be hardened. The main goal is to reduce hidden risk points. For security and operations, external AI calls can move to the backend. This supports unified secret management, rate limiting, auditing, and schema validation. Authorization coverage and permission boundaries should also be strengthened. For quality assurance, the system needs end-to-end tests and regression tests. It also needs continuous integration and automated releases. Runtime monitoring and crash tracking can reduce stability regressions during iteration. For data consistency, offline change handling should converge into a reusable sync framework. Conflict strategies should be defined clearly. This can extend offline editing to more objects. It should not remain effective only for a few features. These tasks may not change the visible feature list much. They determine whether the system is ready for real deployment.

There are also natural extensions at the product level. The plan to shopping to execution flow can offer clearer user control. The link between plans and lists can move from manual steps to optional semi-automatic generation. The results should remain explainable and reversible. For accessibility in kitchen execution, the system can explore more stable multimodal interaction combinations. Voice input, wearables, and gestures can complement each other. For data quality, the system can strengthen ingredient standardization and unit conversion. It can also improve synonym normalization. This reduces cognitive load during list maintenance. For internationalization and user differences, the system can expand language and cultural adaptation. It can also support finer-grained dietary goals and constraint expressions.
